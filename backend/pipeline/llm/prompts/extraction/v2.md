You are extracting a door/opening schedule from an OCR analysis result.

You will be given structured elements, each with an `element_id`, its `text`, and
its table position (row, column, header flag).

For every opening, return one record with these fields:

`door_number`, `size`, `handing`, `finish`, `fire_rating`, `hardware_group`,
`alternate_designation`.

## Rules, in priority order

1. For EVERY field you populate you MUST return the `element_id`(s) of the exact
   source cells or words the value came from. Cite only ids present in the input.
   Never invent an id.

2. Return values EXACTLY as written in the source. Do not normalise, expand,
   convert, or correct them. `3070` stays `3070`. `90 MIN` stays `90 MIN`.
   Normalisation happens downstream.

3. **A size split across two columns is one value.** Door schedules commonly carry
   SIZE as a pair of columns — `W` and `H`, sometimes under a spanning `SIZE`
   header. When they do:

   - Return **both** cell texts, width first, joined by a single space, with
     nothing inserted between them: `3' - 6" 7' - 0"`.
   - Cite **both** cells in `source_element_ids`.
   - Do **not** write `x`, `X`, `by`, or any separator of your own. Do not
     reorder. Do not convert to `3670`.

   When SIZE is a single cell, return that cell alone, exactly as written.

4. If a field is not present, return null with an empty citation list. Never
   guess, never infer from a neighbouring opening, never carry a value down from
   the row above unless the source itself does so with an explicit ditto mark —
   and if it does, cite the ditto mark's element.

5. If a cell is ambiguous, illegible, or spans merged rows in a way you cannot
   resolve, return null and set `needs_review = true` with a reason.

6. Report your own confidence per field as a number in [0,1].

## Why rule 2 matters

If you return `3'-0" x 7'-0"` instead of `3070`, the value can no longer be
grounded against the cited cell text, and a deterministic parser that is correct
100% of the time has been replaced by a model that is correct most of the time.
Extraction returns raw strings. Interpretation is not your job.

## Why rule 3 matters

Returning the width alone is not a partial answer, it is a wrong one: it reads as
a complete size, parses to nothing, and arrives at an estimator as a flagged field
with no indication that half of it is missing on the sheet in front of them.

Rule 3 is not an exception to rule 2. Both cells are returned verbatim; only the
space between them is added, and it is the same space the grounding check uses
when it concatenates your cited elements. That is why the separator must be a
space and nothing else — anything you insert is a character the document does not
contain, and the gate below will reject the whole field for it.

## Why rule 4 matters

Carried-down values are a real pattern in door schedules and a real hazard. A
model that helpfully propagates a fire rating down a column has just invented a
code-compliance claim. Fire rating and handing are zero-tolerance fields: a
missing one is a finding, not a gap to be filled.

## Validation you cannot see

Every field you emit passes through two gates before it reaches anyone:

- **Citation existence** — the ids you cite must be in the set you were given.
- **Value grounding** — the value you return must actually appear in the text of
  the elements you cited, as a string.

A field failing either gate is rejected and flagged for a human. It is never
repaired and never retried. Citing a real element for a value that is not in it
is worse than returning null, because it looks verifiable and is not.
